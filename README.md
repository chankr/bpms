# bpms-ui-design-system-comparison

BPMS（Business Process Management System）向け UI の検証用 monorepo です。  
対象ドメインは、Flowable や Camunda のようなタスク・プロセス中心の業務アプリケーションです。

このリポジトリでは、複数のデザインシステム / UI ライブラリを用いて、**同じ業務領域**を実装します。  
ただし、比較のために無理に画面構成やナビゲーション構成を揃えることはしません。

各 package は、それぞれのデザインシステムの思想、情報設計、ナビゲーション、操作モデルに従って実装します。  
比較対象は「見た目の差」ではなく、以下です。

- 厳格なデザインシステムを素直に反映できるか
- AI 駆動開発と相性が良いか
- ルールベースで設計・実装・レビューしやすいか
- 業務画面として破綻しにくいか
- 感覚的・属人的なデザイン議論を減らせるか

---

## 背景

この検証の背景には、AI 駆動開発を前提にした UI 開発プロセスの整備があります。

AI に業務画面を継続的に実装させるためには、次の条件が重要です。

1. デザインシステムが明確であること
2. ライブラリの制約が明確であること
3. 実装ルールを文章として定義しやすいこと
4. 人間の感覚的な指摘より、ルールに基づくレビューを優先できること

このリポジトリは、そうした前提のもとで「AI に実装させやすい UI 基盤」を比較検証するためのものです。

---

## このリポジトリで比較するもの

- React + MUI
- React + Fluent UI
- React + React Spectrum
- Angular + Angular Material

各 package の詳細は、それぞれの `README.md` を参照してください。

---

## 比較対象の前提

比較対象は **同一ドメイン** ですが、**同一レイアウトではありません**。

比較のために無理に以下を揃えることは禁止します。

- グローバルナビゲーションの位置
- ローカルナビゲーションの形
- 一覧と詳細のレイアウト
- ツールバー構成
- アクション配置
- フィルタ UI の見せ方
- ページ全体の情報密度

各 package は、そのデザインシステムにとって自然な情報設計・画面構成を採用してください。

---

## 最初に作成する画面

最初の対象は **BPMS のタスク管理画面** です。

想定する画面の役割:

- 自分に割り当てられたタスクの確認
- ステータス、期限、優先度、申請種別などによる把握
- 検索 / フィルタ / 並び替え
- タスク詳細への遷移
- 承認 / 差戻し / 保留 / 引き受けなどのアクション
- 一覧中心のオペレーション

ただし、最初の段階ではすべてを実装する必要はありません。  
まずは「タスク一覧を業務画面として破綻なく成立させること」を優先します。

## 実装の基本方針

### 1. デザインシステムを優先する

アプリ都合でライブラリをねじ曲げるのではなく、  
ライブラリ / デザインシステムが前提とする画面構成・部品構成・情報の見せ方を尊重します。

### 2. ルールベースで判断する

以下のような感覚的な判断を主軸にしません。

- なんとなく重い
- なんとなく古い
- なんとなくダサい
- なんとなく使いにくそう

代わりに、以下を明文化して判断します。

- 情報階層は明確か
- 主操作と副操作は分離されているか
- 状態表現は十分か
- 一覧画面として視線移動が過剰でないか
- アクセシビリティを損なっていないか
- デザインシステムの制約に素直か

### 3. AI に渡せる実装ルールを書く

各 package README は、単なる説明文ではなく、  
Claude Code などにそのまま渡せる **実装ルール文書** として整備します。

### 4. 比較のために表面だけ揃えない

同じドメインでも、  
ナビゲーション、情報の塊、操作導線はデザインシステムごとに自然な形が異なります。

この差は比較対象として有益であり、吸収してはいけません。

---

## 全 package 共通ルール

各 package では以下を共通ルールとします。

- 対象ドメインは BPMS のタスク管理画面
- デザインシステムの思想を優先する
- 画面構成を他 package と無理に合わせない
- UI ライブラリの標準的なコンポーネントを優先利用する
- アクセシビリティを壊す独自実装を避ける
- 強引な global CSS override を避ける
- 「見た目合わせ」のためだけのカスタマイズをしない
- Claude Code に実装させる前提で、ルールを文章化する
- README は実装ルールと設計意図の一次資料とする

---

## 評価観点

最終的には以下の観点で比較します。

- デザインシステムの厳格さ
- ライブラリの一貫性
- 情報設計のしやすさ
- 業務画面への適用しやすさ
- AI への指示のしやすさ
- 実装の再現性
- レビューの客観性
- カスタマイズ耐性
- アクセシビリティ
- 保守性

---

## Claude Code への共通指示

各 package で Claude Code に実装させる際は、少なくとも次を守らせます。

- この root README と該当 package README を先に読むこと
- package 固有のデザインシステム思想に従うこと
- 他 package の UI を模倣しないこと
- タスク管理画面を業務画面として成立させること
- 一覧・詳細・操作導線の情報設計を明確にすること
- コンポーネント選定の理由を説明可能にすること
- 感覚的ではなく、ルールに基づいて設計すること

## package README の役割分担

この root README には、全 package 共通の背景・方針・評価観点を記載します。

各 package README には、以下のみを記載してください。

- そのデザインシステム / UI ライブラリの思想
- 採用理由
- package 固有の実装ルール
- package 固有の禁止事項
- 公式ドキュメント URL
- Claude Code に渡す具体的な実装指示
